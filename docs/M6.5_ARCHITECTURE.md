# M6.5 Martial Arts Evolution: architecture and impact

**Base:** `master` @ `e5682eb` (V0.3 merged), all 8 test suites green.
**Branch:** `feature/m6.5-martial-arts`.

## 1. What exists and is reused

| Need | Already there | Reuse |
|---|---|---|
| Per-move frame data, hitboxes, damage, posture, knockback, cancel window, blowback | `CombatData.ATTACK_TABLE` + `Attack` objects | Every new move becomes a row, with no new combat engine |
| Combo graph | `CombatData.CHAINS` (one global table) | Becomes the per-style `chains`; the global table stays as the fallback for style-less unit tests |
| Guard, idle rhythm, footwork | `Stances` (8 kinds, per-stance active idle) | A style points at a stance; new stances are added for Taekwondo and Kickboxing |
| Move animation | `FighterVisual._moves` keyframe timelines, reach limit, spin turn (back kick) | New moves add keyframes; spinning moves reuse the back-kick turn |
| Finisher choreography | `FinisherDirector` beats and pose library | New finishers are new beat lists; the selection becomes style-aware |
| Match flow | PRE_MATCH → … → RESULT, scene reload on restart | Adds STYLE_SELECT before PRE_MATCH |
| Defence, posture, movement, collision, KO | Shared systems | Untouched (universal across styles) |

## 2. Design

**Move IDs.**
- `AttackType` stays the compact in-code key. It is **append-only**: values are never reordered, so they are stable.
- Each `ATTACK_TABLE` row also gets a permanent string `id` (for example `&"lead_hook"`).
- Style data, saves and AI plans refer to moves by `id`. `CombatData.type_for_id()` resolves them.

**`MartialArtStyle` (typed `Resource`, one `.tres` per style in `res://styles/`).** It holds:
- **Identity:** stable `id`, `display_name`, `description`, `category`, `difficulty`, `strengths`, `weaknesses`.
- **Look:** `stance` (an index into `Stances.Kind`).
- **Controls:** `input_map`, mapping slot → move id. Slots are `light` J, `heavy` K, `lead` U, `rising` O, `front` I, `kick` L, `up_kick` W+L, `down_kick` S+L, `back_kick` away+L, `up_heavy` W+K, `down_heavy` S+K. A variant slot with no entry falls back to its base slot (`up_kick` → `kick`, and so on).
- **Air moves:** `air_map`, the same idea for jumps.
- **Combos:** `chains`, mapping move id → follow-up move ids.
- **AI:** `ai_close_plans`, `ai_far_plans`, `ai_preferred_range`.
- **Later batches:** `signature`, `finishers`.
- **Validation:** `validate()` reports unknown moves, chains outside the moveset, and missing required fields. The registry refuses malformed styles.

**`StyleRegistry`.**
- Scans `res://styles/*.tres`, validates each style and orders them by `order`.
- Keeps the player's choice across reloads (a static, like the stance choice today).
- Registering a new style means adding a `.tres` plus any new move rows and keyframes. There is no switch on style names anywhere.

**One gate for legality: `Fighter`.**
- **Player:** the keyboard produces an input *slot*, and the fighter resolves it through its style. An unmapped slot does nothing.
- **AI:** AI intents carry a move, and the fighter rejects any move outside its style.
- **Air:** air conversion uses `air_map`.
- **Combos:** chains use the style's graph.
- A fighter with no style (raw unit tests only) keeps the legacy, unrestricted behaviour.

**Match flow.**
- STYLE_SELECT (cards, details, confirm) → PRE_MATCH (START MATCH; the player already stands in the chosen style's guard, which doubles as the live stance and idle preview) → STANCE_PREP → COUNTDOWN → FIGHTING → FINISHER → KO → RESULT.
- The result screen offers **REMATCH** (same style, straight to PRE_MATCH) and **CHANGE STYLE** (back to STYLE_SELECT).
- **Locking:** styles are fixed from START MATCH on. Q no longer changes anything during a match. The rival is given a different style.

## 4. Future styles (honest notes)

- **Striking styles** (Capoeira, Wing Chun, Kalari, Sanda, Silat strikes) fit this model directly: new rows, keyframes, a stance and a `.tres`.
- **Grappling styles** (Judo, Wrestling, BJJ, Sambo, Hapkido locks) need new *subsystems*, not just data:
  - a synchronized two-fighter interaction (the `FinisherDirector` beat model is the template: it drives both fighters through `begin_scripted`);
  - grip states, throw alignment, escapes and reversals;
  - grounded positions.

  None of this is built speculatively. The extension points are the `category` field on a style and the interaction-director note in `docs/V0.3_PLAN.md`.
